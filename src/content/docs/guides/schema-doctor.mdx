---
title: Schema doctor
description: Review your database structure for problems, in the terminal, in CI, and in the dashboard
---

The schema doctor reviews your database **structure** for problems you can spot without ever reading a row: a table with no primary key, a foreign key with no index, duplicate or redundant indexes, a foreign key whose type does not match the key it references, money stored as a float, and more. It is deterministic and structure-only, with no AI and no network call, so it is safe to run in CI.

There are two front ends for one engine: the **`php artisan truss:doctor`** command in the terminal and CI, and the **Health** panel in the dashboard (the heart icon in the toolbar). The command is called "doctor" and the panel is labelled "Health", but they are the **same feature** running the same rules over the same snapshot, so they always report the same findings.

## The command

```bash
# Review the default connection
php artisan truss:doctor

# A specific connection, as JSON for tooling
php artisan truss:doctor --connection=mysql --format=json

# Be stricter, and fail on warnings too
php artisan truss:doctor --preset=strict --fail-on=warning
```

`truss:doctor` (aliased `truss:check`) prints the findings as a table grouped by table, then exits:

- `0` when clean (nothing at or above the fail level),
- `1` when a finding is at or above `--fail-on` (default `error`),
- `2` on a bad option, a connection problem, or a missing snapshot.

So a migration that introduces a problem can fail the build. Point a commit hook or a CI step at it and a new unindexed foreign key stops being something you find in production.

## Presets and confidence

Every rule declares a **confidence** (high or heuristic) that is kept separate from its severity. High-confidence rules are certain from the structure alone (a table genuinely has no primary key). Heuristic rules are name-based guesses (a `*_id` column that looks like a foreign key but has none, a column called `price` stored as a float): often right, sometimes a deliberate choice.

- `recommended` (the default) runs **high-confidence rules only**, so the first run is quiet and trustworthy. A heuristic finding still fires at its real severity when you turn it on: confidence and severity are independent.
- `strict` runs **everything**, heuristics included.
- `none` runs nothing but the rules you explicitly enable.

Every rule can be enabled, disabled, re-severitied, or ignored per pattern in config, so you tune the signal to your project.

## Engine awareness

A rule can adapt to the database driver. The clearest case is a foreign key with no index: on PostgreSQL and SQLite, which do not auto-index foreign keys, it is an **error**; on MySQL and MariaDB, which do, it is only **info**. You get the right severity for the database you actually run.

## In the dashboard

The dashboard shows the same findings the command does, under the name **Health** (there is no "doctor" button; the heart icon is it). Open the dashboard (`php artisan truss:open`) and the heart button in the toolbar opens a **Health** panel that lists them grouped by table, with the heuristic ones marked as such. Click a table to focus the diagram on it; click the button again to close.

You do not have to open the panel to know something is wrong: every table with a finding carries a small severity badge on the diagram, and the offending **column** is marked on the table itself. Click a marked column to read the finding for that field. The panel can be maximized when a report gets long.

Two switches under `doctor` in `config/truss.php` control the dashboard side:

```php
'doctor' => [
    // ...preset, rules, ignore, fail_on, exclude...
    'dashboard' => (bool) env('TRUSS_DOCTOR_DASHBOARD', true),
    'flag_tables' => (bool) env('TRUSS_DOCTOR_FLAG_TABLES', true),
],
```

- **`dashboard`** (default `true`) shows the Health panel at all. When `false`, the dashboard receives no findings and the panel never appears; the CLI is untouched.
- **`flag_tables`** (default `true`) badges tables with findings on the diagram even when the panel is closed. Set it `false` to keep the diagram clean and surface findings only when you open the panel.

The report rides the schema endpoint the diagram already loads, so there is no extra request, and it is gated by the same `viewTruss` authorization as the rest of the dashboard.

Try it on the **[live demo](/demo/)**: open the Health panel and you will see a handful of foreign keys flagged for a missing index, and `users.email` flagged (heuristically) for having no unique constraint.

## Configuration

Everything lives under `doctor` in `config/truss.php`:

```php
'doctor' => [
    'preset' => env('TRUSS_DOCTOR_PRESET', 'recommended'),  // recommended | strict | none
    'rules' => [
        // 'TRUSS-INT-002' => true,                  // turn a heuristic rule on
        // 'TRUSS-IDX-001' => ['severity' => 'error'], // change a severity
    ],
    'ignore' => [
        // 'TRUSS-IDX-001' => ['audit_log.actor_id'], // silence a known case (fnmatch)
    ],
    'fail_on' => env('TRUSS_DOCTOR_FAIL_ON', 'error'), // error | warning | info | never
    'exclude' => [],                                    // extra tables, on top of excluded_tables
    'dashboard' => (bool) env('TRUSS_DOCTOR_DASHBOARD', true),
    'flag_tables' => (bool) env('TRUSS_DOCTOR_FLAG_TABLES', true),
],
```

See the [configuration reference](/reference/configuration/) for the full key list.

## Rules

Every finding carries a stable **code** (e.g. `TRUSS-INT-003`), shown in both the command output and the Health panel, so you can look it up here, silence it, or change its severity in config. There are thirteen rules across three categories. Heuristic rules are name-based guesses and are **off under `recommended`** (on under `strict`).

| Code | Checks | Severity | Confidence |
| --- | --- | --- | --- |
| `TRUSS-INT-001` | Table has no primary key | error | high |
| `TRUSS-INT-002` | A `*_id` column matches a table but declares no foreign key, polymorphic columns excluded | warning | heuristic |
| `TRUSS-INT-003` | A foreign key column's type differs from the key it references | error | high |
| `TRUSS-INT-007` | A pivot table has no unique constraint on its key pair | warning | high |
| `TRUSS-INT-009` | A polymorphic pair (`*_type`, `*_id`) has no composite index | warning | heuristic |
| `TRUSS-IDX-001` | A foreign key column has no supporting index | error \* | high |
| `TRUSS-IDX-002` | Two indexes cover the same columns | warning | high |
| `TRUSS-IDX-003` | An index is a left prefix of another, so it is redundant | warning | high |
| `TRUSS-IDX-004` | An index duplicates the primary key | warning | high |
| `TRUSS-IDX-005` | A `deleted_at` column is not indexed | warning | heuristic |
| `TRUSS-IDX-006` | An `email` / `slug` / `uuid` / `token` column has no unique constraint | warning | heuristic |
| `TRUSS-TYP-001` | A money-looking column is stored as `float` or `double` | error | heuristic |
| `TRUSS-TYP-002` | An `is_*` / `has_*` column is stored as `varchar` | warning | heuristic |

\* `TRUSS-IDX-001` is engine-aware: an **error** on PostgreSQL and SQLite, which do not auto-index foreign keys, and only **info** on MySQL and MariaDB, which do.

### What `TRUSS-INT-007` counts as a pivot

Two single-column foreign keys are necessary but **not sufficient**, or every entity table with two relationships would be flagged. A profile table with a `user_id` and a `plan_id` is not a many-to-many join, and the composite unique key the rule suggests would be wrong there.

So Truss also asks whether the table carries its key pair and little else. It counts the columns that are not the pair, not `id`, and not `created_at` / `updated_at` / `deleted_at`. A table whose primary key **is** the pair, or which has no primary key at all, may carry one such column. A table with its own `id` primary key must carry none, because a table with its own identity is treated as an entity unless it has nothing else in it. Any other primary key is never a pivot.

The rule also stays quiet when a unique index already covers **any part** of the pair, since a unique `user_id` makes `(user_id, plan_id)` unique on its own. Nullable columns do not count, because most engines allow repeated `NULL`s in a unique index.

**A genuine pivot carrying two payload columns is missed on purpose.** A finding you never see costs you nothing, and a wrong one here recommends a migration that loses rows.

Use these codes in `doctor.rules` (to enable, disable, or re-severity a rule) and `doctor.ignore` (to silence a known case per table or `table.column`). More rules land in later phases.

## Caveats

- **Structure only.** The doctor reads the same cached snapshot the diagram uses and never queries row data. It cannot know selectivity or query patterns, so it reviews structure, not performance.
- **Heuristics are guesses.** They are off by default for a reason. Turn them on when you want them, and ignore the deliberate exceptions per pattern.
- **Deterministic, for a given version.** No AI, no network. The same schema and the same version of Truss always yield the same findings, so a diff in CI output is a real structural change. Across an upgrade it may not be: a rule that gets narrower reports less on a schema nobody touched. See [Upgrading](#upgrading-and-a-changed-rule) below.

## Upgrading, and a changed rule

Rules are calibrated against real schemas, so a release can change what the doctor reports on a database nobody touched. The first run after an upgrade is the one to read carefully: a smaller report is usually Truss having got quieter, not your schema having improved.

**v1.10 narrowed `TRUSS-INT-007`.** Two single-column foreign keys stopped being enough to call a table a pivot. Measured across the twelve real Laravel applications that could run both versions, the rule fired 69 times before and 14 times after, and 56 of those 69 were wrong: profile tables, settings tables and one-to-one joins that are not many-to-many at all. One of them recommended a unique constraint that would have capped a user at a single budget. Those twelve schemas are also the ones the new rule was tuned on, so read the counts as a measure of what changed, not as a forecast of what your own report will do.

What that means for you:

- **A CI job on `--fail-on=error` may now pass where it failed**, on a schema you have not changed. That is the intended outcome, not a regression.
- **Findings you had suppressed in `doctor.ignore` may no longer fire.** A stale ignore entry is harmless, but it is worth pruning so the next real finding is not silently covered by it.
- **Some genuine pivots are now missed on purpose.** A pivot carrying two payload columns escapes the rule. A finding you never see costs you nothing; a wrong one recommends a migration that loses rows.

The same release stopped `TRUSS-INT-002` asking for a foreign key on polymorphic columns, which contradicted `TRUSS-INT-009` inside the same report, so a morph-heavy schema also gets a shorter report than it did.

Findings and counts are only comparable between runs of the **same** version. If you track them over time, record the Truss version alongside the number.
